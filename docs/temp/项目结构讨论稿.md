# 项目结构讨论稿

本文档是讨论稿，不是最终结构约定。

后续如果结构方案确认，再把结论写回：

- `.ai/guide/目录约定.md`

## 背景

当前项目可以运行，但目录组织还停留在“先把功能放进去”的阶段。

现状大致是：

- `src/plugins/`
  - NoneBot 入口
- `src/langchain_app/`
  - `chat`
  - `history`
  - `identity`
  - `infra`
  - `qq`
  - `rag`
  - `tools`

这套结构现在能用，但后面 agent、tool、history、platform adapter 再变多，会出现一个问题：

- `langchain_app` 这个名字更像“框架目录”
- 而不是“项目业务目录”

## 我当前的判断

我比较倾向于你上个项目那种更清晰的分层方式。  
也就是：

- 入口层
- 应用层
- 适配层
- 基础设施层

这个方向比继续扩 `langchain_app` 更稳。

## 当前结构的问题

### 1. 根目录命名偏框架，不偏业务

`langchain_app` 这个名字的问题是：

- 它强调的是 LangChain
- 但项目真正长期稳定的，不是 “LangChain” 这个词
- 而是：
  - agent
  - rag
  - history
  - identity
  - adapter

如果以后换实现细节，这个名字会越来越别扭。

### 2. QQ 适配层挂在 `langchain_app` 下不自然

比如现在：

- `src/langchain_app/qq/event_utils.py`

从职责上看，它其实不是 LangChain 逻辑，而是平台适配逻辑。  
所以更自然的归属应该是：

- `src/adapters/qq/`

### 3. agent 与 rag 以后都会继续长

现在 `chat`、`rag`、`tools` 还不多，但后面如果继续补：

- agent service
- agent prompt
- tool registry
- memory strategy
- rag ingest
- rag query
- knowledge management

都会继续长。  
这时候按“应用层”组织会更清晰。

## 我建议的目标结构

我当前更推荐的目标结构是：

```text
bot.py
src/
  plugins/                  # NoneBot 入口层
  app/                      # 核心应用层
    agent/
    chat/
    rag/
    history/
    identity/
    tools/
  adapters/                 # 外部平台适配层
    qq/
  infra/                    # 基础设施层
    config.py
    llm.py
    logger.py
    prompt_loader.py
```

## 这样分层的好处

### 1. `plugins` 只管接入

这里专门放：

- 命令注册
- 消息入口
- 参数提取
- 调用 service

不要把复杂业务写在这里。

### 2. `app` 只管业务逻辑

这里放：

- agent
- rag
- history
- identity
- chat
- tools

它表达的是“这个项目到底在做什么”。

### 3. `adapters` 专门承接平台差异

这里放：

- QQ 事件字段解析
- 群号、用户号、显示名处理

后面如果你再接别的平台，也很自然。

### 4. `infra` 保持稳定

这里继续放：

- 配置
- 模型工厂
- 日志
- prompt loader

这一层本来就比较稳。

## 当前目录到目标目录的映射

如果后面要迁移，我建议按下面理解：

```text
当前                         -> 目标
src/plugins                  -> src/plugins
src/langchain_app/chat       -> src/app/chat
src/langchain_app/rag        -> src/app/rag
src/langchain_app/history    -> src/app/history
src/langchain_app/identity   -> src/app/identity
src/langchain_app/tools      -> src/app/tools
src/langchain_app/qq         -> src/adapters/qq
src/langchain_app/infra      -> src/infra
```

## 我对迁移节奏的建议

我不建议一次性全量重构。  
更合适的是两步：

### 第一步

先确认是否接受这个目标结构。

如果接受，再把它写回正式文档：

- `.ai/guide/目录约定.md`

### 第二步

后面只要碰到某个模块，就顺手迁一部分。

比如：

- 先迁 `qq -> adapters/qq`
- 再迁 `infra -> src/infra`
- 再迁 `chat / rag / tools`

这样风险更低。

## 当前我的结论

如果只是讨论方向，我更支持：

- 不继续扩大 `langchain_app`
- 最终转成：
  - `plugins`
  - `app`
  - `adapters`
  - `infra`

但这份文档现在只是讨论稿，还不是最终方案。

## 待确认问题

后面如果你确认要推进结构调整，我建议你重点拍板下面 3 件事：

1. 是否接受 `app / adapters / infra` 这套分层
2. 是否要逐步淘汰 `langchain_app` 这个根目录名
3. 是一次性重构，还是按模块逐步迁移
