# 后续任务规划

本文档只描述 `yun_bot` 后续还值得做的内容，不重复描述当前已完成部分。

## 规划原则

- 每次只推进一小步
- 先保证 demo 可演示，再补能力
- 能用简单方案就不用复杂方案
- 不为了未来可能性提前做过多抽象

## 阶段划分

## 阶段 1：把最小 agent 跑稳

这是当前最优先阶段。

### 目标

- 让 agent 的群聊表现更稳定
- 降低不必要的 `rag_search` 调用
- 提高日志可读性，方便排查

### 建议任务

- 优化 agent system prompt
- 优化 agent 对“闲聊 / 知识查询” 的分流判断
- 补充更清晰的 agent 日志
- 观察几轮真实群聊，收集错误案例

### 完成标准

- `@机器人` 的日常聊天可稳定回复
- 需要资料的问题能较稳定调用 `rag_search`
- 日志足够支持问题排查

## 阶段 2：补知识库管理能力

当前 `/upload` 只能录入字符串，后面可逐步增强知识管理。

### 候选任务

- 增加“清空本群知识库”
- 增加“重建本群知识库”
- 增加“查看本群知识库状态”
- 为知识录入补充更清晰的 metadata

### 暂不建议现在做

- 单条知识精确删除
- 单条知识精确更新
- 复杂权限系统

如果后面真的要做单条删除和更新，就需要补：

- `source_id`
- chunk ids
- registry

## 阶段 3：补更多录入方式

如果你后面觉得仅靠 `/upload 文本` 不够，再做这层。

### 候选任务

- 收录引用消息
- 收录文件
- 扫描群资料目录并灌库

### 当前建议

这部分现在不是最高优先级。
先把“字符串录入 + 群聊 agent + /rag 检索”用顺更重要。

## 阶段 4：管理 agent 的历史与记忆

现在的历史是你自己手动存储和读取的，后面可以继续演进。

### 当前状态

- 历史由项目代码手动写入 JSON
- agent 不会自动持久化记忆
- 每次运行时重新读取群历史

### 后续方向

- 限制历史长度
- 历史裁剪
- 历史摘要压缩
- 评估是否切到 `checkpointer + thread_id`

### 当前建议

先不要急着做摘要记忆。
等 agent 真出现明显的上下文过长问题，再处理。

## 阶段 5：补更多 tool

当 `rag_search` 跑稳后，可以继续给 agent 增加工具。

### 候选任务

- 时间工具
- 天气工具
- 简单查询类工具

### 原则

- 每次只加 1 个工具
- 每加一个都要确认日志和行为是可解释的
- 不要一次塞很多 tool，避免调试成本过高

## 当前不建议优先做的事

- 复杂多 agent
- 复杂 planner / executor
- 复杂记忆压缩
- 复杂权限体系
- 旧接口兼容层

这些内容对当前 demo 收益不高，但会明显增加维护成本。

## 推荐推进顺序

建议你后面按这个顺序走：

1. 稳定最小 agent 的行为与日志
2. 增加知识库管理命令
3. 视需要增加更多知识录入方式
4. 再考虑历史长度控制和记忆治理
5. 最后再扩展更多 tools

## 一句话总结

后续路线不是“继续堆功能”，而是：

- 先把当前最小 agent 调顺
- 再补知识库管理
- 再补录入方式
- 最后再处理复杂记忆和更多工具

这样最适合现在这个 demo 项目的节奏。
